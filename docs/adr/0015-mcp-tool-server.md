# ADR 0015: The MCP tool server

* **Status:** accepted
* **Date:** 2026-10-29

## Context

The assistant answers questions about current orbital and space weather conditions and pulls live numbers through a read only MCP tool server over `query-api` ([architecture](../architecture.md)). The [threat model](../security/threat-model.md)'s MCP section (T8.1 to T8.7) and the hardening items `SEC-MCP-01` to `SEC-MCP-07` and `SEC-ACK-07` set the rules: every tool read only and mapped to exactly one read endpoint, no URL, host, path or free form query parameter, typed and bounded parameters checked server side, static tool definitions, per tool rate limits, internal only exposure with authenticated callers, and an identity toward `query-api` that the acknowledgement endpoint refuses.

### What I verified about the library

Versions checked on Maven Central on 2026-10-29: Spring AI 2.0.2 is the newest release, and its `spring-ai-starter-mcp-server-webmvc` brings `mcp-spring-webmvc` 2.0.2 and the MCP Java SDK (`io.modelcontextprotocol.sdk:mcp`) 2.1.0. The starter's own pom names Spring Boot 4.1.2; in this repository the parent manages Boot 4.1.1, and `./mvnw -pl mcp-server dependency:tree` resolves every Spring artifact to the parent's versions. Everything below was read in the 2.0.2 and 2.1.0 source jars and then run in `ToolServerIntegrationTest`.

1. **Transports.** `spring.ai.mcp.server.protocol` takes `SSE`, `STREAMABLE` (the default) or `STATELESS`. `STATELESS` serves Streamable HTTP without sessions: `WebMvcStatelessServerTransport` answers every `POST` on its own and answers `GET` with `405`, so there is no server sent event stream and no `Mcp-Session-Id`. The endpoint is `spring.ai.mcp.server.streamable-http.mcp-endpoint`, `/mcp` by default.
2. **No caller check of its own.** The transport's `ServerTransportSecurityValidator` defaults to a no op, and the starter sets none, so authenticating callers and refusing browsers is left to the application.
3. **Input schemas are enforced.** The SDK's server builders validate every call's arguments against the tool's input schema by default (`validateToolInputs`, true) and answer a failure as a tool error without calling the handler. An unknown tool name is a JSON-RPC error.
4. **Tools can be plain beans.** The stateless server collects every `List<McpStatelessServerFeatures.SyncToolSpecification>` bean. The annotation scanner (`spring.ai.mcp.server.annotation-scanner.enabled`) and the resource, prompt and completion capabilities each have a property to turn them off.

## Decision

1. **Where it lives.** A new Maven module and container, `mcp-server`, a Spring Boot service next to `query-api`. Rejected: tools in process inside the assistant (the protocol hop would be decorative), tools inside `query-api` (the tool surface would share a process with the acknowledgement write path).
2. **Library.** Spring AI's MCP server starter for Spring MVC, 2.0.2, on the parent's Boot 4.1.1. Tomcat is pinned to 11.0.26 as in `query-api`. The tools are built as `SyncToolSpecification` beans with hand written JSON Schemas, not from annotations, so each schema states its bounds exactly; the annotation scanner, resources, prompts and completions are off. Rejected: the MCP Java SDK directly, which would mean writing the servlet transport wiring that the starter already provides.
3. **Transport and callers.** Streamable HTTP in its stateless form (fact 1) on an internal Compose network, `tools`, with no published port. Every request needs `Authorization: Bearer` with the token in the Compose secret `mcp_server_token`; the service keeps only the token's SHA-256 digest, compares in constant time, and refuses to start when the file is missing or holds fewer than 32 printable characters. A request carrying an `Origin` header is refused with `403` even with the token, since no browser has a reason to call it. Rejected: stdio (the assistant would have to spawn the tool server, which does not fit separate deployables on EKS) and the stateful transport (a session to manage and nothing gained by it).
4. **Tools.** One per read endpoint, listed with their endpoints in [mcp-server/README.md](../../mcp-server/README.md): current space weather, space weather history, current screening run, recent alerts, one alert, one catalog object, the watchlist, and passes of a watchlist object. Never the session, acknowledge, or acknowledgement history endpoints. Recent alerts come from a new REST endpoint, `GET /api/alerts/recent` ([REST API](../api/rest.md), section 11), which serves the same query as GraphQL's `alerts` field, so every tool maps to one REST read (`SEC-MCP-01`). Names, descriptions and schemas are constants in `ReadTools`.
5. **Identity toward query-api.** No credential: the tool server sends a plain `GET` with no cookie, no token and no redirect followed, and its client has no method for any other request. Every endpoint the tools call is public, and acknowledgement refuses any request without the operator's session, so the anonymous viewer is the read scoped identity `SEC-MCP-07` asks for. A caller's token is never passed on. `SEC-ACK-07` is closed by a `query-api` test sending what the tool server could send at its worst (a bearer token and an XSRF pair it made up itself, which passes the XSRF check) and getting `401` before any query, and by a tool server test that every request it makes is a `GET` with no `Authorization`, `Cookie` or `X-XSRF-TOKEN` header.
6. **Limits.** Parameter bounds mirror `query-api`'s own (page size 1 to 200, a history range of at most 7 days with years 1000 to 9999, catalog numbers 0 to 999,999,999, `event_id` at most 512 code points with no control character, `scale` and `kind` from their fixed lists, cursors as base64url of at most 256 characters). They are stated in each input schema (fact 3) and checked again in code before any call, together with the rules a schema cannot state (`to` after `from`, `satellite` required for R and S and refused for G). A fixed window per tool of one clock minute, 30 calls to start, refuses the next call as a tool error until the minute ends. A call the schema check refuses never reaches the handler, so it is not counted; it never reaches `query-api` either.

## Consequences

* Compose gains a `tools` profile with the `mcp-server` service and an internal `tools` network that `query-api` joins. The `core` profile runs as before and needs no token. `deploy/mysql/make-secrets.sh` now also writes `deploy/secrets/mcp_server_token`; it keeps every file that exists, so running it again leaves the MySQL passwords alone.
* The token is one shared secret. Rotating it means replacing the file and restarting the tool server and its caller. The assistant, when it is built, is the one caller and reads the same secret.
* The rate limit is counted in one process, which holds while the tool server runs as one replica, as Compose runs it. More replicas are a new decision.
* T8.6 also asks for a per request cap on tool calls; that cap belongs to the assistant, which decides how many calls one question may make, and is decided with it.
* On EKS the service gets no public Service or ingress, and `SEC-MCP-06` is checked again against the manifests when they are written.
* The container's memory limit, 384 MiB, is a starting value, not a measurement; it is measured with the rest of the stack before the cloud environment is sized.
* Every Java Dockerfile now copies `mcp-server/pom.xml`, since the reactor lists the module.
