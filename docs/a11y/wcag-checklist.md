# WCAG 2.2 AA checklist, operator dashboard

This is the accessibility checklist for the SpaceFlux operator dashboard, checked against WCAG 2.2 at levels A and AA. It covers two things that must agree: the canonical design in [`docs/design/dashboard.html`](../design/dashboard.html) and the Angular app in [`dashboard/src`](../../dashboard/src), which is built from it. Colors, type, focus and motion rules come from [`docs/design/tokens.md`](../design/tokens.md).

First checked on 2026-10-06 and rechecked twice on 2026-10-07 against the working tree of that date, after the fixes listed under [Findings](#findings). In the first recheck the local API was an older build than the app's queries, so the screening panel could only be checked in the design file. In the second recheck the API was built from the same tree and answered every query: the space weather panels showed live data (three scales at "none"), the screening panel showed a current run with no close approach and 8 suppressed pairs, and no alerts were stored. The close approach table with rows and the alert list were therefore still checked in the design file only. Acknowledgement controls and the sign in form were drawn in the design but not built in the app yet, so their rows were then checked against the design only; they were built and checked on 2026-10-22, see below.

The Watchlist passes panel was added on 2026-10-10 and checked the same day, in both files, against an API built from the same tree. The live watchlist held one object (ISS (ZARYA), 25544) with two computed passes, neither clipped. The other states (a pass clipped at the window start, one clipped where the search ended, one with two maxima, an object whose computation failed, an element set too old, and an empty list) were shown by adding them to a real answer inside the browser, so the app rendered every state with its own code.

The alert views were added on 2026-10-12 and checked the same day, in both files: the kind filter and Load older on Recent alerts, the held list and its "Show new alerts" bar, the New badge, the alert page (`/alerts/{event_id}`), one object's close approaches (`/objects/{norad_cat_id}/alerts`), and the object links in the screening table, the passes headings and the alert page. No API was running, so the browser answered each GraphQL request itself by executing it against the server schema (`query-api/src/main/resources/graphql/schema.graphqls`) with the committed test fixtures (`dashboard/src/testing/fixtures.ts`), and live notices came from a stand in for the subscription socket that speaks the graphql-transport-ws protocol. The list held 45 alerts made from the six fixture items with distinct ids, so Load older had two further pages. The alert views were rechecked on 2026-10-13 the same way, after the fixes listed under F28 to F34, with the fixtures of that date, a second time the same day after the fixes listed under F37 to F39, a third time after the fixes listed under F40 to F42, and a fourth time after the fix listed under F43.

Sign in, sign out and acknowledgement were built on 2026-10-22 and checked the same day, in both files: the sign in form in the header, sign out, the session that ends on its own, the acknowledge controls and the note form on Recent alerts items and on the alert page, and the alert page's History. The app was built from the working tree of that date and served with a small local stand in for the API: GraphQL requests were executed against the server schema with the committed fixtures, as for the alert views, and the sign in, sign out, acknowledgement and history endpoints of [`docs/api/rest.md`](../api/rest.md) were answered from a small in memory state that could be told to answer wrong credentials, HTTP 429 with `Retry-After: 120`, HTTP 500, HTTP 401, or to hold each answer for a set time. No subscription socket was offered, so no live notice arrived during these checks. The wording for an acknowledgement whose answer never came (a timeout) was still being written and is not checked here. They were rechecked the same day the same way, after the fixes listed under F44 to F50, on a new build that adds the session time limit notices and keeps a note being written when the session ends; the session answer of the stand in then also gave the session's end time, and the browser clock was moved on to reach the notices.

## How it was checked

* **Automated rules.** axe-core in headless Google Chrome, tags `wcag2a`, `wcag2aa`, `wcag21a`, `wcag21aa`, `wcag22aa`, plus `best-practice`, on both the design file and the running app, at 320 and 1280 CSS px. The first recheck used axe-core 4.14.0 with playwright-core 1.63.0, the second axe-core 4.12.1 with playwright-core 1.62.1. Result both times: no violations on either. One "needs review" item remains on the design only (`color-contrast` on table cells whose background axe could not resolve; the colors involved are `text-secondary` on `surface-1` and `surface-3`, 8.58 and 6.99).
* **Keyboard walk.** A script pressed Tab through each page at 1280, 640 and 320 CSS px wide and recorded, for every focused element, its outline and whether its center or corners were covered by any other element (`document.elementFromPoint`).
* **Reflow and zoom.** Horizontal overflow measured at 320 CSS px (reflow) and at 640 CSS px, which is the layout a 1280 px window shows at 200 percent zoom.
* **Text spacing.** The WCAG 1.4.12 values (line height 1.5, letter spacing 0.12 em, word spacing 0.16 em, paragraph spacing 2 em) injected as a style sheet at 320 and 640 px, then every element with hidden overflow checked for clipped content and the page checked for sideways overflow.
* **Reduced motion.** Computed animation and transition values read with `prefers-reduced-motion: reduce` emulated and without it.
* **Live regions and pausing.** A mutation observer recorded every change to each `role="status"` element while the page refreshed, paused and resumed. A request counter confirmed that no GraphQL request leaves the page during 75 s of pause (20 s in the second recheck), and that resuming refreshes all three queries at once. To see the failure paths without stopping any service, the browser answered one query at a time with HTTP 503 while the others reached the API, then let it through again.
* **Color.** Contrast, color vision simulation and CIEDE2000 recomputed with a separate implementation written for this check, not with the script in `docs/design/tools/`. The CIEDE2000 code reproduces all 34 published test pairs of Sharma, Wu and Dalal (2005), downloaded from the author's site, to four decimals. Every contrast ratio, every color vision figure and every grayscale figure in `tokens.md` was reproduced.

* **Passes panel.** axe-core 4.12.1 with playwright-core 1.62.1, same tags, at 320, 640 and 1280 CSS px, on the design file, on the app with the live answer, on the app with every object state, and on the app with the passes request answered with HTTP 503 from the first load. The accessibility tree was read from Chrome. The Refresh passes button was pressed from the keyboard with the request held for 2.5 s, to read its state, focus and look while the request was out, and pressed again four times during it (Enter, Enter, Space, a mouse click) while a request counter ran. A mutation observer recorded the panel's status line through two refreshes that succeeded and two that failed. A request counter watched 65 s of the one minute refresh and a pause and resume.

* **Live alert announcements.** Added 2026-10-11 and so far checked by reading the code and its unit tests only, not in a browser or with a screen reader: the recent alerts panel template, the announcement wording, the list merge, the data layer's pause and resume, and the subscription client. Rows that rest on this review say "static". Checks M9 and M10 settle them.

* **Alert views.** axe-core 4.12.1 with playwright-core 1.62.1 in headless Google Chrome 151, same tags, at 320 and 1280 CSS px on the console with held and New items, the alert page (close approach and G level), the not found and refused id states, the object page, the no catalog entry and refused number states, and the design file. Reflow and the text spacing values at 320 and 640 px on the same pages. Focus was read after every route change (a title link, an object link, Back to the console, browser Back), with the scroll position and `document.title`. A mutation observer recorded every `role="status"` and `role="log"` region through a filter change, three Load older presses (one answered with HTTP 503), a failed alert load and two presses of Try again, live notices under a filter, and leaving and reentering the console. For the held list, focus was put on a title link inside the list while notices arrived, then moved with Shift+Tab to "Show new alerts", pressed with Enter and with a mouse click. Target spacing was measured for every link, button and input smaller than 24 px. In the 2026-10-13 recheck, focus and the `h1` text were sampled every 50 ms through each route change, with the answer held for 1 s; browser Back to the console was repeated 16 times with no alert arriving and 22 times with two alerts arriving while away, with every scroll event, scroll call and focus call recorded; and the browser clock was moved on 10 minutes to see the New marks clear. In the second recheck that day, browser Back to the console was repeated 25 times with two alerts arriving while away and 16 times with none; the page's stale notice line was recorded from the moment it was drawn on each of seven returns (nothing changed, paused on the alert page, still paused, resumed there, a space weather refresh failing while away with the browser clock moved on past the one minute refresh, the failure lasting, and the refresh recovering); the summaries for alerts that arrived while away or while paused were read under each filter, including the counts that can be short; and Load older was pressed to the end under each filter, with its first press answered with HTTP 503. In the third recheck that day, the log entries for live alerts were recorded with focus entering the list 100, 600 and 1500 ms after an alert joined it, and with groups that mixed listed and waiting alerts; the New marks were counted after pauses that brought 0, 1, 19, 20 and 25 alerts, and one in which the previous top alert had left the store; browser Back with two alerts arriving while away was repeated 25 times and with none 12 times, with the distance from the focus ring to the window edge measured, and Tab and Shift+Tab onto title links just outside the window were measured the same way; and the stale notice line was recorded on the first visit to the console after opening an alert page or an object page directly. In the fourth recheck, the stale notice line was recorded with an animation frame counter running, from the moment it was drawn, 20 times each at 1280 and 320 px on four paths to a first visit (an alert page opened directly, then Back to the console; an object page opened directly, then Back to the console; an alert page opened directly, its object link followed, browser Back, then Back to the console; and `/` loaded directly), then 5 times each on returns with nothing changed, a return after pausing on the alert page, a second return with nothing changed, and a first visit made while paused; axe ran on the console after a direct load and after such a first visit, on a close approach alert page, and on the design file, at 320 and 1280 px. axe then ran on every route at 320 and 1280 px: the console under each filter and with held and New items, the alert page for a close approach, a G level and a no data sample, an alert not found, a refused event id, a failed alert load, the object page, no catalog entry, a refused number, and an unknown path. axe reported no violations on any of the pages above at 320 or 1280 px; its one needs review item, on the console only, is `color-contrast` on table cells partly scrolled out of their table's box, whose colors are `text-primary`, `text-secondary` and `text-muted` on `surface-1` (14.83, 8.58 and 5.73).

* **Sign in and acknowledgement.** axe-core 4.12.1 with playwright-core 1.62.1 in headless Google Chrome 155, same tags, at 320 and 1280 CSS px: the console signed out, with the sign in form open and showing the wrong credentials message, signed in with the acknowledge controls, with an item's failure line and Try again, with a note form open, and the alert page signed in and signed out with a History of 25 entries. Sideways overflow measured at 320 px on the same pages. The keyboard paths were driven with key presses and focus read after each one: opening the form, Escape, Cancel, an empty press, wrong credentials, a backoff, Enter during the backoff, Escape while a sign in was out (held 1.5 s), a sign in that succeeded, Acknowledge, Unacknowledge, a failure, Try again failing and then succeeding, a note pushed over the limit, Escape in the note, a press while over, Cancel, sign out, Load older on History to its end (held 0.6 s), and History's Try again (held 0.5 s). A mutation observer recorded every `role="status"` element's text and class. A session that ends on the server was shown with the browser clock moved on past the one minute check, once with focus on a title link and once with focus on an Acknowledge button, and once by an acknowledgement answered with HTTP 401. In the recheck, axe ran again on every page above and also with the idle notice shown (320 and 1280 px), the 8 hour notice shown, and a kept note on the console (320 and 1280 px) and on the alert page. With the browser clock moved on while updates were paused, the idle notice was read at 27 and 28 minutes, Stay signed in was pressed with the session check answered with HTTP 500 and held 0.6 s, then answered, and the notice was reached a second time; the 8 hour notice was watched in real time with an end 10.5 minutes away, since the page places that end on its own clock from each session answer and a moved clock defeats it. The window's scroll position and a focused title link's place on screen were read just before and just after the idle notice appeared, with the header scrolled out of view, at 1280 and 320 px, with and without the browser's scroll anchoring. A kept note was made three ways: the minute check finding the session gone with focus in the note, an "Acknowledge with note" press answered with HTTP 401, and the minute check on the alert page with focus on Back to the console.

Automated tools cannot settle everything. The checks that need a person are listed under [Checks that need a person](#checks-that-need-a-person).

## Status key

* **Pass**: checked and met, with the evidence named.
* **Fail**: not met; the finding says what to change.
* **Fail, accepted**: not met, and kept on purpose for a stated reason; the row says what the page does instead.
* **Open**: needs a person (see the numbered checks) or a decision before it can be marked.
* **N/A**: the dashboard has no content of that kind.
